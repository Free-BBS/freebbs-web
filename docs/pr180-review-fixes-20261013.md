# PR #180 审核问题修复

原审核基线：`ec96b2befcca13e80b21eda23b0db1d23a938543`。本轮仅处理审核指出的两项问题及回归覆盖，不部署、不改线上课程或用户记录、不自动合并。

## 修复

- **资料来源接口**：把 `requireAuth` 纳入已有 `try/catch`。鉴权数据库异常返回通用 503，不泄露内部错误；拒绝登录仍返回 401，不读取知识点或个人资料。严格未处理拒绝模式的独立 Node 子进程验证同一 PID 存活并恢复正常请求。
- **研究并发提交**：quota 初始化改为保留原值的 `ON DUPLICATE KEY UPDATE`，直接取得排他锁，避免 `INSERT IGNORE` 共享锁升级互锁。已有窗口与额度不重置，重复请求不额外消耗额度。
- **死锁恢复边界**：仅 `ER_LOCK_DEADLOCK` 在回滚、释放连接后重跑完整事务，总计最多三次，退避 10/20ms。连接失败、锁等待超时、业务冲突、提交结果不确定和回滚失败均不自动重试。
- **持续回归**：路由子进程用例接入 `test:learning-companion`；真实研究 MySQL 用例接入隔离 MySQL CI 的必运行清单。`--research-only` 支持定向验证，并要求成功用例、零失败、零跳过，不以内存或 execute mock 代替实库锁验证。

## 复现与验证

旧代码的独立路由用例在鉴权抛错后收到 `ECONNRESET`；新代码返回 503，同一子进程继续响应。旧代码在真实 MySQL 的相同 requestKey 阶段提交、不同 requestKey 反馈并发场景均复现 `ER_LOCK_DEADLOCK`；新代码通过。

实库使用全新临时数据目录、随机专用 named pipe、禁用网络的 MySQL 8.0.46，不读取生产数据库配置。并发用例先锁住已存在的 quota 行，确认两个事务都在数据库中排队，再放行，避免顺序执行冒充并发。验证相同请求只产生一份作答与一次额度消费，以及十组不同请求的反馈均保留两份数据；同时覆盖迁移重复执行、本人隔离、固定判分、UTC 延迟门槛、删除回执和保留期。
