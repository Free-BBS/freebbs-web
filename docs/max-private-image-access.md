# 私人 Max 生成图片访问修复

本次改动只修改本地准备版本，不直接部署。无需新增依赖、数据库迁移或密钥。

## 访问与历史兼容

私人问问 Max 生成图片保存到 `UPLOAD_DIR/.max-images`；客户端只收到 `/api/ai/images/max-image-所有者ID-时间-随机串.webp`，读取时必须通过现有登录和政策确认，且当前用户为图片所有者。管理员没有额外通行权限。登录令牌只放在 Authorization 请求头，不拼接到图片 URL。

历史 `/uploads/max-image-*` 链接仍可供原所有者查看，不重写历史会话、不删除或迁移旧文件。直接请求旧链接同样经过权限校验；匿名访问、其他账号和其他管理员不能读取私人图片。读取失败时显示重新加载按钮。

新版讨论区实际生成的图片在回复成功写入数据库后，由服务器写入 `UPLOAD_DIR/.max-images/.publications` 中的发布记录，绑定文件、所有者、帖子和评论。读取时同时检查这条记录与帖子的删除、隐藏、登录可见状态；评论删除后也不再提供公开访问。用户名、正文引用或模型复述都不能生成发布记录，别人把私人图片链接粘贴到自己的帖子、评论或冒充 Max，不会取得图片访问权。普通头像、课程或社区公开上传文件沿用原有访问规则。

历史 Max 生成图片没有这类发布记录，全部先仅供原所有者访问，其中原来公开的 Max 讨论图片对其他人会暂时不显示。这是旧数据无法可靠区分私人生成与讨论生成的兼容限制。需要恢复公开的旧图，应先由原所有者或负责人核实出处和公开意愿，再通过正常讨论图片上传与发布流程重新发表；本次不依据用户名或 Markdown 自动补写发布记录。旧文件不删除。

前端以经过认证的请求获得图片内容，再生成当前页面的 Blob 链接供展示、查看原图和下载。退出或切换账号时清空图片及原图/下载链接，撤销 Blob 链接并取消未完成请求。已下载或已被他人保存的文件无法通过服务器权限变更收回。

## 本地验收

1. 账号 A 打开更新前已有的私人图片对话，确认展示、查看原图、下载正常；再测试一张新生成图片。
2. 复制聊天 Markdown 中原始 `/uploads/max-image-*` 或 `/api/ai/images/*` URL，在未登录窗口直接访问，不能看到图片。
3. 用账号 B 和非所有者管理员登录，打开相同 URL 或引用该链接的消息，不能看到私人图片。
4. 账号 A 加载图片后退出或切换账号，原图片、查看原图与下载链接应立即清除。
5. 检查普通讨论图片仍正常展示。当前开启讨论区审核时会暂停 Max 的讨论区自动回复，不需要为了测试而关闭审核。新版 Max 讨论图片的发布记录、隐藏帖子及删除回复后的权限变化已由自动化回归覆盖。旧版 Max 生成图片对非所有者暂时不可见，按上文人工核实后重新发布。

自动化检查：`node --test backend/max-image-access.test.js backend/max-images.test.js scripts/max-image-results.test.js`。
浏览器检查：`node scripts/check-max-image-access-browser.js`，需要本地可用 Playwright（可用 `PLAYWRIGHT_MODULE` 指向安装路径）及 Chromium（可用 `CHROME_PATH` 指定路径）。检查使用临时目录、合成图片和合成账号，启动真实前端代理与隔离后端，不调用模型或正式数据库。

## 正式部署前的代理确认

仓库前端 Node 服务会把 `/api/` 和 `/uploads/` 转发到后端并保留 Authorization。台式机按这套方式运行无需更改代理。正式网站仍需验证外层 Nginx/CDN 没有直接用 `alias`/静态目录提供 `/uploads/max-image-*` 或 `.max-images`，没有用公开缓存绕过后端；这些路径必须经过本次后端鉴权（私有目录直接请求返回 404）。如旧私人链接曾被 CDN 缓存，还需失效对应缓存。后端响应使用 `private, no-store`；本次本地代码不能自行证明或修改服务器反向代理配置。

更新前备份上传目录。回退到不带该鉴权的旧后端会重新暴露旧生成图片路径，因此本修复上线后不应直接回退到旧版静态处理。
