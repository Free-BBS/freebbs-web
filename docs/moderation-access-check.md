# 审核上线权限只读检查

此流程用于确认 GitHub 部署账号的权限，不能用 SSH 登录账号 `zbx` 的权限代替。流程不会开启审核，也不判定已经具备上线条件。

工作流合并到 `main` 后，在 GitHub Actions 选择 **Moderation access check (read only)**，点击 **Run workflow** 并选择 `main`。需要仓库写权限；如 `production` 环境要求批准，按既有规则批准这次只读检查。其他分支不会执行此正式入口。

流程复用现有 `DEPLOY_HOST`、`DEPLOY_USER`、`DEPLOY_SSH_KEY`，以及部署端口、目录、后端服务名变量。无需新增数据库密码或模型密钥。SSH 主机校验沿用既有部署的 `ssh-keyscan` 方式，不禁用 StrictHostKeyChecking。

检查脚本经 SSH 标准输入交给服务器现有的 `/usr/bin/node` 执行，不在服务器安装或保存脚本。JSON 报告显示在最后一个步骤的日志中：

| 字段                 | 含义                                                                                                    |
| -------------------- | ------------------------------------------------------------------------------------------------------- |
| `deploymentIdentity` | 实际执行检查的 UID、GID 和组，不输出连接主机或密钥                                                      |
| `paths`              | 配置文件、计划使用的私有目录及父目录的类型、所有者数字 ID、权限、符号链接实际路径和部署账号访问权限     |
| `service`            | 后端服务加载/运行状态、服务账号、工作目录、环境文件路径及文件系统限制，不包含环境变量值、启动命令或日志 |
| `sudoPolicyQueries`  | 对既有后端 restart/status 精确命令的非交互授权查询；没有执行这些命令                                    |

`query_allowed` 只表示忽略认证缓存后 `sudo -n -k -l` 查询成功，不能单独证明实际重启一定无需密码。`not_confirmed` 可能是权限不足、查询本身需要密码或工具不可用，不等于“没有任何 sudo 权限”。

`missing` 表示路径不存在；`unavailable` 表示无法读取元数据，不能将权限拒绝当成目录不存在。检查主体是部署账号，不是后端服务账号；即使部署账号可写，也不能据此判断后端服务可访问。`plannedPrivateDirectory` 固定检查 `/var/lib/free-bbs/moderation-private`，不代表已经读到正式配置正在使用这个目录。

流程不读取环境文件正文、用户内容、数据库或模型配置，不调用模型，不执行迁移，不创建生产目录、不修改权限、不重启服务。SSH/sudo 查询仍可能产生正常系统审计日志。退出成功表示完成检查，不代表所有权限齐备；`productionReadiness` 固定为 `not_evaluated`。

**合并影响：** 当前 Deploy 在 `main` 每次更新时会自动部署。合并本 PR 因而仍会触发既有部署和服务重启；检查流程自身只接受手动运行，不修改 Deploy。

如需合并前检查，可由维护者在专用临时分支将已有 `deploy.yml` 完整替换为上述只读工作流，并将分支条件限定为该诊断分支；核对固定提交后，通过已注册的 Deploy 工作流显式指定该分支运行。临时版本不得保留部署任务、push 触发器或启用配置的步骤，不合并到 `main`。不要运行 `main` 的 Deploy 来代替只读检查。若没有 Actions 调度权限或环境规则不允许此分支，应停止并交付 PR，不能绕过保护。
