# 发展端管理员模块设计

## 目标

将发展端现有“系统设置”改造为只供发展端负责人使用的“管理员模块”。页面以用户权限管理为核心，采用与主站学习端一致的清晰卡片、暖白明亮模式和深青灰暗色模式，完整表达组织身份层级，同时避免把 Role、Tag、权限绑定等底层实现直接暴露给日常管理员。

本阶段建立完整的身份目录、互斥规则和管理界面。各身份对应的细粒度功能权限将在后续需求中确定；现有已经生效的业务权限保持兼容。

## 权限边界

发展端访问继续分为三个等级：

- `none`：不在发展端白名单，访问发展端时仍看到主站施工页面。
- `member`：可以进入发展端，但不能看到管理员模块入口，直接访问 `/development/admin` 时跳回发展端首页，调用 `/api/development/v1/admin/*` 时返回 `403`。
- `lead`：发展端负责人，可以进入管理员模块、编辑用户访问等级和身份，并切换身份预览。

“平台管理员”是独立身份，不等同于发展端负责人：

- 平台管理员不能进入管理员模块，也不能编辑用户权限。
- 平台管理员将在后续独立建设的“系统设置”中管理除用户权限以外的系统功能。
- 当前阶段勾选平台管理员只保存身份，不额外授予尚未设计的系统功能权限。

所有写入操作继续由后端校验发展端负责人身份，不能只依赖前端隐藏入口。

## 信息架构

侧栏入口和页面标题统一改为“管理员模块”。页面不再展示横向的底层治理标签页，默认直接进入“用户权限”。

管理员模块保留两个用户可见功能：

1. **用户权限**：页面主体，管理访问等级、组织身份、平台管理员和代表队队长。
2. **操作记录**：页面右上角的次要入口，以抽屉或独立面板展示权限变更记录；不占据主导航。

以下现有界面从管理员模块中移除，但后端基础能力暂不删除，以免影响现有数据和后续维护：

- 用户与授权
- 角色与权限
- Tag 定义
- 模块与负责人
- 业务数据入口
- 运行状态

操作记录只展示与用户权限管理直接相关的事件，包括访问名单、组织身份、平台管理员和代表队队长的新增、修改与移除。

## 用户权限界面

桌面端使用左右分栏，窄屏改为上下布局：

- 左栏为用户目录，包含搜索框和用户列表。
- 右栏为当前用户的权限编辑器。

每个用户列表项展示：

- 头像、用户名、显示名称与学号；
- “不可访问”“可访问”或“发展端负责人”状态徽标；
- 已选身份的简短摘要；
- 未保存修改提示。

右侧编辑器从上到下排列：

1. 用户基本信息和“以此身份预览”按钮；
2. 发展端访问等级；
3. 平台管理员独立勾选项；
4. 辅导员身份；
5. 电子系学生会；
6. 电子系团委；
7. TMS 电子系分会；
8. 电子系科协；
9. 电子系学生媒体中心；
10. 代表队队长，固定放在全部组织身份之后。

组织使用折叠面板。面板标题显示已选数量和摘要，例如“电子系学生会 · 已选 3 项”。每个组织单元使用分段按钮选择职位：同一单元最多选择一个职位，再次点击当前职位可清除；不同组织单元可以同时选择。财务负责人是独立兼任按钮，不占用其他职位。

编辑器底部设置固定操作条，显示“有未保存修改”或“权限已同步”，并提供“放弃修改”和“保存权限”。切换用户时如存在未保存修改，页面要求先保存或放弃，避免误丢数据。

## 身份目录

身份目录由共享的类型化配置生成，前端用它渲染分组，后端用它验证合法值与互斥关系。每个条目包含稳定键、中文名称、所属组织、互斥组、显示顺序和暂定权限配置。

### 辅导员

同一互斥组，最多选择一个：

- 团委书记
- 团委辅导员
- 实践辅导员
- 科创辅导员
- 学生发展辅导员

### 电子系学生会

- 顶层职位：执行主席、主席团，二选一。
- 文艺中心：负责人、主任、部员，三选一。
- 体育中心：负责人、主任、部员，三选一。
- 联络中心：负责人、主任、部员，三选一。
- 权益发展中心：负责人、主任、部员，三选一。
- 学生会财务负责人：独立兼任按钮。

### 电子系团委

- 组织组：副书记、组长、组员，三选一。
- 新生组：副书记、组长、组员，三选一。
- 志愿组：副书记、组长、组员，三选一。
- 实践组：副书记、组长、组员，三选一。
- 人文组：副书记、组长、组员，三选一。
- 扬帆计划组：顾问、小导、学员，三选一。
- 团委财务负责人：独立兼任按钮。

### TMS 电子系分会

同一互斥组，最多选择一个：

- 顾问
- 会长
- 会员

### 电子系科协

- 科协主席：独立顶层身份。
- 办公室：副主席、部长、部员，三选一。
- 软件部：副主席、部长、部员，三选一。
- 硬件部：副主席、部长、部员，三选一。
- 学培部：副主席、部长、部员，三选一。
- 项目部：副主席、部长、部员，三选一。

### 电子系学生媒体中心

- 创意设计部：顾问、部长、部员，三选一。
- 影音策划部：顾问、部长、部员，三选一。
- 新媒体与记者团部：顾问、部长、部员，三选一。

### 独立身份

- 平台管理员：单独勾选，不能访问管理员模块。
- 代表队队长：单独勾选；勾选后必须至少选择一支现有代表队，可以同时负责多支代表队。

代表队的新增、修改和停用不属于管理员模块。本阶段只读取现有代表队。后续独立“系统设置”将允许平台管理员、体育中心负责人和体育中心主任维护代表队目录。

## 数据与兼容策略

组织身份继续复用现有角色分配存储，代表队队长继续复用带 `sports_team` 范围的 `sports.team_captain` Tag 分配，发展端访问等级继续使用 `development_access_grants`。不为同一事实建立第二套平行数据表。

共享身份目录扩展 `RoleKey`，并为每个可见身份定义互斥组。后端更新用户权限时执行以下验证：

1. 所有身份键必须来自可分配身份目录；
2. 每个互斥组最多出现一个身份；
3. 代表队队长开启时至少有一个有效代表队 ID；
4. 未开启代表队队长时代表队 ID 列表必须为空；
5. 只有发展端负责人可以调用读取完整用户目录和更新权限接口；
6. 至少保留一位发展端负责人。

现有文艺、体育、联络、权益发展中心角色保持原有功能权限。现有团委、科协和 TMS 粗粒度角色保留为隐藏的兼容身份，避免已有授权丢失；新加入的团委、科协和 TMS 细分身份暂按所属组织和层级继承对应的旧权限档位。辅导员、学生会顶层、财务负责人、学生媒体中心和平台管理员在细粒度权限方案确定前只作为身份记录，不额外获得业务写权限。

后续确定详细权限时，只调整身份到权限规则的映射，不改变用户已经保存的组织身份，也不重做管理界面。

## API 变更

`GET /api/development/v1/admin/development-users` 的用户记录继续返回访问等级、角色和代表队 ID。身份摘要由前端通过共享身份目录从 `roles` 计算，接口不重复返回派生字段，也不返回密码、邮箱或其他与权限编辑无关的敏感字段。

`PUT /api/development/v1/admin/development-users/:uid` 接收：

- `accessLevel: 'member' | 'lead' | null`
- `roles: RoleKey[]`
- `captainTeamIds: string[]`

平台管理员包含在 `roles` 中；`platform.super_admin` 仍由 `accessLevel: 'lead'` 管理，不能直接放入角色数组。请求在一个数据库事务中同步访问等级、角色和队长范围，并写入一条包含变更前后摘要的审计记录。

## 视觉规范

管理员模块沿用发展端和主站学习端的语义颜色，不再使用独立的黑色治理主题。

- 明亮模式：暖白页面背景、白色卡片、浅灰边框、深青正文、青绿色主操作，少量暖金用于负责人状态。
- 暗色模式：深青灰页面背景、略亮的青灰卡片、低对比边框和暖白正文，避免纯黑大面积背景。
- 选中职位使用实体浅青底和清晰描边；悬停只加深同一色系，不出现亮蓝或突兀高饱和色。
- 所有列表、按钮和折叠区在 320px 宽度下不得横向溢出。
- 用户列表和权限编辑器使用统一圆角、间距和字号层级，减少大面积装饰渐变。

## 错误与状态

- 用户目录加载失败时保留搜索条件并显示重试按钮。
- 保存失败时保留本地编辑状态，不覆盖用户选择。
- 服务器返回互斥冲突或无效代表队时，在对应折叠区就地显示错误。
- 保存成功后重新读取该用户，确认数据库结果并清除未保存标记。
- 同一次保存中的访问等级、角色和代表队范围必须全部成功或全部回滚；本阶段沿用现有数据库事务保证原子性。

## 测试范围

- 身份目录完整性：键唯一、显示顺序稳定、所有互斥组有效。
- 后端校验：组内多选被拒绝，跨组多选成功，平台管理员不能调用管理员接口。
- 代表队队长：开启时要求选择队伍，多队可保存，关闭时清空范围。
- 权限边界：`member` 看不到入口、前端路由跳转、后端接口返回 `403`；`lead` 可以完整编辑。
- UI 交互：搜索和选择用户、折叠组织、互斥按钮、跨组多选、未保存状态、保存失败恢复。
- 主题和响应式：明暗模式颜色契约以及窄屏无溢出。
- 回归：现有业务角色权限、身份预览和最后一位发展端负责人保护保持有效。

## 本阶段不包含

- 为每个新身份最终确定详细的业务操作权限；
- 新增或编辑代表队；
- 平台管理员可访问的独立“系统设置”；
- 删除现有底层治理 API 或数据库表。
