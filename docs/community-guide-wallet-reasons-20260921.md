## 钱包审计及修复

### PR #104 追加：新手导引完成奖励

- 完整新手导引完成后，登录用户可获得一次性 **10 电元 + 10 磁元**，新老用户规则相同。
  已有当前/旧版完整导引完成记录但尚未领取的用户，可在导引首页领取；不会在只读请求中补发。
- 奖励独立于五项访问任务与各次更新短导览。重复播放、跨版本完成、多设备并发或网络重试
  都只对应一份永久账号奖励；不占每日互动奖励额度，不增加热力。
- 新增迁移 `047_onboarding_rewards.sql`、只读状态与领取接口。两币余额、账本原因、
  唯一回执在同一事务中处理，失败全部回滚；账本标题为「新手导引完成奖励」。
- 前端正常完成完整导引后领取并刷新余额，失败可重试；老用户有独立领取入口。
  游客和短导览不自动领奖，跳过最后一站不再生成新的完成记录。
- 本地预览支持同样的领取、旧记录兼容与去重语义；回归覆盖金额、余额快照、并发、重试、
  多账号隔离与事务回滚。真实数据库条件测试需在隔离 MySQL 中运行，不使用生产数据。

原有数据库触发器记录了真实收支和前后余额，但不会自动从业务表补全标题、原因。
因此“钱包余额变动 / 该笔变动未附加原因说明”不是刷新即可消除的问题。

| 影响货币的操作                           | 本次结果                                                 |
| ---------------------------------------- | -------------------------------------------------------- |
| 商城购买（包括橡胶棒、微分器、收藏品等） | 记录商品名、支付币种及实际金额；双币价格两条流水均注明   |
| 激光器充值                               | 记录天数、日费及每种货币的实际支出                       |
| 连续签到、好运加成、福袋补发             | 写明签到或好运奖励原因；沿用同日去重                     |
| 发帖、帖子三种反应、回帖获赞             | 写明奖励来源和实际所得；保留每天 3 磁元封顶              |
| 精华帖子、精华回帖                       | 独立说明精华奖励；取消再设置不重复发放                   |
| 管理员批量奖励、帖子奖励                 | 保留管理员填写的奖励名称、原因；加强只标注本笔流水的约束 |
| 微分器双向兑换                           | 扣本金与收入分别解释方向；不改变既有手续费和热力规则     |
| 普通/黄金鱼骨出售、羊毛摩擦              | 保留原有说明，统一新流水检查                             |
| 付费改名                                 | 写明旧昵称、新昵称和费用；免费改名不产生空流水           |
| 管理员开户和余额调整                     | 记录操作人、初始余额或调整前后金额；零余额变化不入账     |
| 历史签到规则与旧热力兑换接口             | 保留行为，补充说明；旧热力扣款与说明同事务               |

所有注释在原业务事务内完成。调用方锁定用户后，以当前读取取得最新流水 ID，
余额变化后仅注释该用户更大的新 ID，且不覆盖已有来源。缺少本笔触发器记录时抛错回滚。
ID 在 SQL 中转成字符串，避免 BIGINT 经 JavaScript Number 转换丢精度。
数据库余额快照仍为真实值；本地模拟现在也逐笔记账，不再合并整个操作或虚构通用商城原因。

不根据金额反推旧原因，不补旧流水。手工 SQL、外部写库程序仍只能由触发器记录余额，
不会凭空生成业务原因。若增加新的货币入口，需要在同事务接入这两个 helper。

### 工作台生成预览失败：只读诊断，尚未修改业务逻辑

- 固定当前日期为 2026-09-21，本地真实解析器将“22号下午4点开会，持续2小时”
  解析为 9 月 22 日北京时间 16:00–18:00 的“开会”。路由以空日程 stub 返回 200，
  只读取一次日程，不调用 Agent，也不写入日程。
- 前端截图原文来自 `backend/workbench-schedule-planner.js` 的兜底异常处理。
  路由在解析前先查询已有日程，注入 `ER_WRONG_ARGUMENTS`、`ER_BAD_FIELD_ERROR`、
  `ECONNREFUSED` 都能得到相同提示；这些仅是模拟错误映射，不是线上故障证据。
- 可疑兼容点：预览与确认两条 SQL 均以 `pool.execute` / `connection.execute`
  传入数值 `501` 作为 `LIMIT ?`；本地 mysql2 编码器将 JS 数字发送为 DOUBLE。
  [mysql2 维护者说明](https://github.com/sidorares/node-mysql2/discussions/2652)
  记录了该类型与部分 MySQL 的 LIMIT 参数预期不兼容、产生 `ER_WRONG_ARGUMENTS`
  的问题。需用生产错误码或独立真实 MySQL 验证，不能仅凭截图认定根因。
- 另有独立兼容风险：进入 Agent 的非规则表达会因提示中的 FREE BBS 文本触发
  通用网站代码/历史上下文补充，并附加自然语言答复风格，与计划提取的严格 JSON
  要求并存。该问题不在上述明确时间表达的执行路径中，不能用来解释本次截图。
- 未连接生产数据库、调用真实 AI 或创建线上日程；本机 Docker daemon 不可用，
  尚无本轮真实 MySQL 复现。请核对后端服务日志“生成计划失败”之后的错误码。

   旧热力兑换接口也应增加请求幂等键，避免超时重试多扣。
2. 生产发布限制为主分支，PR 使用独立预览；展示实际发布的 commit，便于定位版本。
   当前工作流允许手动把功能分支部署生产，这解释了合并前已经能看到 #102 功能。
3. 讨论问题增加采纳、已解决/重新开启的闭环；悬赏需要完整冻结、结算、退款设计后单独实现。
4. 通知在现有通知页基础上增加类别/组织订阅、偏好与静默时段，并与发展端做权限联调。
5. 首页接入真实通知摘要，并逐步完善公开帖子/通知分享卡片；不是新增假通知演示。
