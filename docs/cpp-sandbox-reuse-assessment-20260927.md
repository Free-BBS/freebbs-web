# 复用 Max 既有代码沙盒的可行性分析（2026-09-27）

## 结论

优先核查并复用现有沙盒是合理的，比立即引入第二套代码执行服务更适合当前阶段
接口层面有明确复用基础，但还没有拿到沙盒实现或生产部署证据，不能据此认定已经满足实验室需求
本轮仍封闭独立 C/C++ 实验室并显示“规划中”；以下为后续方案分析，不是已实施或已开放的功能

## 已确认事实

- Git 历史：0ccb85f，2026-05-02，add coderun，已引入 postSandboxRun
- Max 页面将回复中的 Python、C、C++ 代码块加上“运行”按钮，由用户主动点击触发
- 前端 handleCodeRunClick → POST /api/code/run → 后端 requireAuth、代码非空/长度检查 → SANDBOX_URL/run
- 请求含 language、code、uid、timeout；结果读取 stdout、stderr、exit_code/exitCode 和图片文件列表
- SANDBOX_URL 默认 http://127.0.0.1:8000，可由部署覆盖；这不是外部免费编译器地址，也不是生产健康证明
- 未找到沙盒自身的服务代码/容器配置，无法确认实际使用 GCC/g++、Clang、具体版本及隔离设施
- Max 的模型负责对话；现有运行按钮把代码交给沙盒，并非模型在自身推理中真实执行程序

## 可复用与缺口

| 项目           | 当前证据                                                 | 实验室接入前需要做的事                                                            |
| -------------- | -------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 登录与请求入口 | 已有登录鉴权、用户 ID、256 KiB 代码上限及代理            | 复用公共执行适配层，保留 Max 客户端兼容                                           |
| C / C++ 模式   | 前端与后端都把 C/C++ 归一为 cpp                          | 确认沙盒支持独立 C；明确标准、编译器版本、编译参数白名单，避免把 C 当 C++ 编译    |
| 标准输入       | 当前代码未传 stdin                                       | 在沙盒支持的前提下贯通输入字段；先支持一次性输入，终端交互另议                    |
| 结果与诊断     | 有 stdout、stderr、退出码；页面将有 stderr 判失败        | 区分编译诊断、程序标准错误、退出码与基础设施错误；警告/正常 stderr 不应一律判失败 |
| 超时           | 向上游传 timeout，并在 fetch 响应头返回后清除请求计时器  | 截止时间覆盖响应体读取；检查上游是否真终止编译/运行进程；取消请求不等于进程已停止 |
| 输出与资源     | 网关代码限制源码长度，未见该路由的输出体积/内存/并发配置 | 核查沙盒部署，再补执行/输出/CPU/内存/进程/磁盘限制、并发队列与每用户限流          |
| 隔离与持久文件 | 带用户 uid，图片输出读取有用户路径检查                   | UID 不等于执行隔离；须验证进程、文件、网络、权限、执行后清理和不同用户间隔离      |
| 服务部署       | 仅看到服务地址契约                                       | 核实服务归属、源码版本、编译器版本、运行方式、容量、健康检查及维护责任            |

表中缺口指当前仓库可见实现，并不表示远端沙盒一定缺少相应能力；需由部署证据确认
本轮未更改 Max 的旧代码路径，也没有发起真实执行请求或把学生代码上传到任何服务

## 推荐接法与验收顺序

1. 取得现有沙盒仓库/部署说明及编译器版本信息，不需要提供密码、Token 或密钥
2. 在隔离测试环境确认现有协议和能力；如原有沙盒符合隔离要求，优先复用，不先新增 Piston/Judge0 服务
3. 实验室和 Max 共用执行适配层；必要时用版本化接口/新增可选字段，保留老客户端契约
4. 使用自建测试程序验证纯 C 与 C++、输入/EOF、编译警告/错误、正常 stderr、非零退出、超时与取消后终止、输出上限、用户隔离和适度并发
5. 确认足够的服务器容量和维护责任后，再向用户提出开放建议；并非有服务器就自动满足安全与稳定条件
6. Max 辅导作为单独功能验收，遵守“给指导，不直接输出答案”，与真实编译结果分开展示

正式开放前不把用户代码直接交给网站主进程通过 exec 执行，也不把公共第三方运行 API 当作默认后端
