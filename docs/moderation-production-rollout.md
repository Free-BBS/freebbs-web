## 3. 开启人工审核，验证正式数据路径

将 `DISCUSSION_MODERATION_ENABLED=true`，`AUTO_ENABLED` 仍为 false。此时新提交会等待人工决定；安排负责人在线，避免正常用户长时间等待。先读取修改后的配置运行只读检查：

```bash
sudo bash -c 'set -a; . /etc/free-bbs/free-bbs.env; set +a; exec runuser -u freebbs-backend -- /usr/bin/node /data/www/free-BBS/scripts/moderation-production-preflight.js'
```

脚本只查询表名、负责人数量、暂停状态和路径可访问性，不调用模型、不执行迁移、不打印数据库口令/API Key。`maxImageStorage` 还核对上传目录及符号链接实际指向是否属于部署保留位置；无法确认或处于会被覆盖的位置时，不判定具备验收条件。该判断仅相对于运行脚本所在检出目录，必须在实际部署目录执行；`deploymentRootVerified=false` 与 `proxyChecked=false` 提醒仍需核对实际部署目标、Nginx/CDN 和缓存。`--configuration-only` 可跳过数据库连接；退出码 2 表示尚未具备人工审核验收条件，不代表脚本写入失败。只看脚本退出码无法判断能否开启自动审核，必须同时检查下面对应的结果字段。

`readyForManualAcceptance` 检查正式配置、Node 主版本、存储可访问性、审核表、隐私确认表 `privacy_policy_acceptances`、导出审计表 `ai_dialog_export_audit` 及负责人；`readyForAutomaticAcceptance` 在此基础上还要求正式自动审核开关、供应商核对标记及暂停状态。表名查询限定在当前数据库和明确的检查清单，不读取确认记录或聊天内容。脚本不会验证供应商密钥是否可用、模型质量、隐私弹窗交互、导出范围和审计内容，也不会替运营方确认供应商安排。`/api/health` 返回 `ok: true` 也不能替代这些功能验收。

确认 `configurationIssues` 为空且 `readyForManualAcceptance=true` 后再重启；若检查未通过，先修正配置或目录权限，保留当前服务运行。

```bash
sudo systemctl restart free-bbs-backend
curl --fail --silent --show-error http://127.0.0.1:3001/api/health
```

在正常 HTTPS 网站验证：普通账号通过通知进入自己的内容详情，不可见负责人入口，直接访问负责人接口仍被拒绝。登录时完成对应的隐私政策确认后，发帖和评论不再弹出旧的讨论区说明；未完成确认的业务请求不会自动被当作已同意。负责人能收到通知并查看私有图片，未登录或非授权用户读不到图片；人工通过、拒绝、撤回均正常。

隐私确认验收至少使用一个新注册账号和一个上线前已有的账号。首次完整弹窗必须包含当前政策全文，拒绝不能建立确认记录；第二次登录只勾选即可，且仍能打开全文。换账号不沿用上一账号的同意状态。确认记录必须由已认证的服务端账号产生，不采纳请求体中的其他用户 ID；过期的政策版本不能写为当前确认。

导出验收在管理员页面选择用户，再选择该用户的会话、时间和调查理由。现有聊天消息没有独立时间戳，所以时间范围按**会话最后更新时间**筛选，开始时间包含、结束时间不包含；导出的是选中会话的完整记录，不应把它描述成只导出某时间段的单条消息。当前上限为 10 位用户、100 个会话、31 天和 25 MB。旧 GET 导出请求应返回 405；目录查询、导出和审计查询均须校验管理员权限，普通用户不能因知道接口地址而读取数据。使用虚构对话核对成功和失败记录，审计记录不复制聊天正文或密钥。

## 4. 开启自动审核验收

确认供应商安排和数据告知已落实后，再将 `DISCUSSION_MODERATION_PROVIDER_REVIEWED=true`、`DISCUSSION_MODERATION_AUTO_ENABLED=true`。先重复上述只读预检查，确认 `readyForAutomaticAcceptance=true`、`paused=true`、负责人数量大于 0，再重启后端并检查健康状态。管理员在工作台开启自动审核。

只用网站管理人员的虚构验收内容各测一次：普通建议、明确违规、政治关键词、心理求助、正常图片、不可读图片。核对 Qwen/Kimi、通知和最终发布状态。含图自动通过后务必验证图片队列与撤回。不要在正式网站跑批量模型评测或把真实学生内容加入测试样例。

若仅放开文字，可暂设 `DISCUSSION_MODERATION_AUTO_IMAGES_ENABLED=false`；含图内容仍转人工。后台没有自动切换到 GLM 的机制，供应商故障时转人工，后续更换模型需要重新验收。

## 5. 故障处置与回退

优先在工作台暂停自动审核，保持人工处理。若后台不可访问，先停止后端，核对任务及暂停状态后再恢复；不要直接启动第二个 worker。模型故障、未知类别或结果校验失败不能当成通过。

仅需停用模型时设 `DISCUSSION_MODERATION_AUTO_ENABLED=false` 并重启，保留 `DISCUSSION_MODERATION_ENABLED=true`，新稿件继续人工审核。不要同时关闭总审核开关来处理模型故障，否则会回到原有直接发帖路径。

代码回退前先停止自动 worker，优先采用保留私人图片鉴权、隐私确认与受限导出的修复版本。不能直接部署不含这些保护的旧版本：旧 `/uploads/max-image-*` 链接可能重新被公开读取，旧导出接口也可能恢复无范围读取。必须使用旧代码应急时，先在服务端或入口代理阻断相关私人图片和 AI 导出路径，并失效可能存在的公开缓存；仅隐藏页面按钮不构成访问保护。核对匿名、其他账号和非所有者管理员无法读取私人图片后，才能恢复对应入口。

保留审核表、私有图片（含隐藏目录与发布记录）、公开上传和最新数据库。不要删除新表，也不要用上线前数据库备份覆盖上线后新增的正常帖子与账户；如必须恢复数据，需单独制定差异恢复步骤。

证据清理、备份保留和供应商留存是三件事。本站 90 天清理任务不代表备份或供应商副本也同时清理。上线后检查待审积压、图片复核队列和错误日志，由负责人安排日常值守。
