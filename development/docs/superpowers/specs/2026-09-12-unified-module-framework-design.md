# FreeBBS 发展端统一模块框架设计

日期：2026-09-12
状态：已完成会话内设计确认，等待书面规格复核

## 1. 背景与目标

发展端已经具备经验库、信息与咨询、趣缘群体、活动、联络资源、体育代表队、财务治理和平台治理等模块的可运行原型。现有实现验证了权限、状态流转和 MySQL 数据边界，但多个业务页面已经增长到 500–800 行，阅读、编辑和管理操作集中在同一页面，继续直接追加功能会增加理解和维护成本。

本轮工作先建立统一页面框架，再在框架上同步整理各模块。目标是：

1. 视觉风格与 FreeBBS 主站学习端统一；
2. 页面简洁、可读，允许业务深入但不堆叠复杂交互；
3. 复杂模块拆成列表和详情子页面，轻量模块保留单页；
4. 补充首期确实需要的字段与接口，不建设大而全的平台；
5. 保留现有权限关闭式失败、作用域隔离、审计和服务器确认状态；
6. 把大页面拆成职责单一、可以独立测试的组件。

## 2. 非目标

本轮不包含：

- 主站页面或生产服务器改造；
- 发展端正式生产发布；
- 外部课题组、企业账号体系；
- 私信、关注、全站动态流等完整社交网络能力；
- 财务报销、票据、打款等完整财务系统扩展；
- 重写既有权限引擎或绕过发展端授权使用主站管理员身份；
- 为统一代码风格而进行与本轮页面无关的全仓库重构。

## 3. 设计原则

### 3.1 阅读优先

进入模块后首先看到可浏览、可搜索的业务内容。创建、编辑、审批和批量操作只在用户拥有对应权限时出现。页面不展示无权限的管理按钮，也不向业务用户暴露作用域类型、资源 ID 或状态码等技术字段。

### 3.2 深而不杂

每个页面围绕一个主要任务组织信息。复杂业务通过详情页承载深度，不通过在列表页持续增加折叠面板承载深度。单个页面只保留一个突出主操作，其余操作使用次级按钮或紧凑菜单。

### 3.3 统一而不僵化

所有模块复用页面标题、筛选、状态、异步状态、编辑抽屉和确认对话框等基础组件。业务详情仍使用各模块自己的领域组件，不把所有数据强行塞进同一种万能卡片。

### 3.4 权限与界面一致

前端隐藏无权入口只用于改善体验，后端继续执行最终授权。所有写操作以服务器响应为准；权限过期、并发冲突或请求失败时，界面保留最后一次服务器确认状态。

## 4. 学习端视觉契约

发展端沿用学习端的视觉语言，而不是复制某一张具体页面：

- 背景使用浅灰白，主要内容使用白色或轻微暖色纸面；
- 主色使用深青色，强调色保持低饱和；
- 中文正文保持高可读性，标题使用学习端已有的字体层级；
- 容器使用细描边、12–14px 圆角和轻阴影；
- 卡片之间使用留白区分，不依赖厚重阴影或玻璃效果；
- 状态同时显示文字与低饱和色，不只依赖颜色；
- 表单字段使用业务名称，不显示内部标识；
- 动效只用于抽屉进入、状态反馈和加载，不使用持续装饰动画；
- 桌面端优先使用紧凑列表和双栏详情，移动端转换为单栏卡片。

工作台继续作为登录后的默认页面，但侧栏不重复显示“工作台”入口。

## 5. 统一页面架构

### 5.1 共用组件

建立以下小型共用组件：

- `ModulePageHeader`：模块标题、说明、主操作；
- `FilterBar`：搜索、少量关键筛选和排序；
- `StatusBadge`：统一业务状态；
- `AsyncState`：加载、空数据、无权限和失败状态；
- `ResponsiveRecordList`：桌面紧凑列表、移动端卡片；
- `EditorDrawer`：轻量模块创建和编辑；
- `ConfirmDialog`：归档、退出、撤销等确认操作；
- `PermissionActions`：根据授权上下文渲染操作区；
- `DetailSection`：详情页内一致的内容分区。

共用组件只处理展示和通用交互，不包含领域 API 路径或业务状态流转。

### 5.2 模块内部边界

每个模块按需要拆成：

```text
pages/       路由页面和页面级数据组合
components/  领域列表项、详情分区和编辑器
api/         请求函数和 DTO 适配
model/       显示模型、标签与纯函数
permissions/ 页面操作所需的权限判断适配
```

不要求一次性机械创建全部目录。只有当模块存在对应职责时才创建文件，避免空层级。

### 5.3 数据流

```text
路由页面读取身份和参数
→ API 层请求服务器
→ 页面把 DTO 转换成显示模型
→ 列表或详情组件展示
→ 编辑器提交业务字段
→ 服务器验证权限、状态和作用域
→ 返回确认记录
→ 页面更新并重新同步列表或详情
```

页面不在客户端猜测写入成功，也不自行生成最终状态。

## 6. 路由与模块范围

### 6.1 经验库

继续使用单页和编辑抽屉：

```text
/knowledge
```

保留 General 与社工组织分区，补充分类、标签、摘要、最近维护时间、维护者和搜索。内容类型继续使用流程、常见问题、联系人、活动复盘和注意事项。首期不增加复杂富文本编辑器、协同编辑或 Agent 自动发布。

### 6.2 信息与咨询

拆成同一模块下的清晰子页面：

```text
/information/announcements
/information/consultations
/information/triage
/information/proposals
/information/proposals/:proposalId
```

`/information` 默认进入公开信息页，既有链接不失效。

补充负责人、处理期限和可读进度。公开信息、个人咨询、处理队列与提案池使用同一模块导航，但不在一个页面同时展开。权益发展中心继续拥有维护权限；普通同学只看到公开信息、自己的咨询和允许公开的提案内容。

### 6.3 趣缘群体

继续使用单页目录和局部详情：

```text
/interest-groups
```

补充分类、简短介绍、负责人、公开联系方式和关联活动。加入申请、退出和管理员处理保留现有状态流。首期不建设群聊、私信、关注或独立动态流。

### 6.4 活动

列表与详情分离：

```text
/events
/events/:activityId
```

列表页负责搜索、组织、时间与状态筛选；详情页承载介绍、时间地点、报名信息、筹备进度、时间线、比赛预览和管理操作。补充报名截止时间、人数上限、联系人和组织选择器。首期不建设复杂票务、支付或座位系统。

### 6.5 联络揭榜

原“联络资源”调整为真实问题揭榜社区：

```text
/liaison
/liaison/problems/:problemId
```

列表页采用酒馆任务板的信息结构，但遵守学习端的克制视觉风格。详情页围绕一个真实问题形成轻量协作社区，具体见第 7 节。

### 6.6 体育代表队

列表与队伍详情分离：

```text
/sports
/sports/:teamId
```

列表页展示队伍、赛季和公开简介；详情页承载训练安排、成员、队长、CSV 导入和签到。首期补充赛季与训练安排，不增加赛事报名、成绩统计和通知系统。

### 6.7 财务与平台治理

财务模块本轮只接入统一页面外壳，不扩充业务字段。平台治理继续独立并仅对最高管理员显示，只调整共用视觉组件，不扩大入口或权限。

## 7. 联络揭榜详细设计

### 7.1 首期定位

课题组和企业把真实问题交给联络中心，联络中心在发展端代录。首期不允许外部主体直接登录或发布；数据模型保留来源信息，以便后期增加“外部提交、内部审核”。

### 7.2 问题字段

问题包含：

- 标题与简短摘要；
- 背景说明；
- 来源类型与公开来源名称；
- 领域标签和所需能力；
- 目标与期望成果；
- 限制条件；
- 开始时间与可选截止时间；
- 公开对接方式；
- 内部联系说明；
- 当前状态、录入人、审核人和审核时间。

内部联系人、私人电话和未获准公开的信息不得出现在公开字段中。

### 7.3 状态流转

```text
draft → pending_review → open ↔ paused
            ↓          ↓       ↓
         rejected     closed → archived
            ↓
           draft
```

发展端负责人或团委书记任意一人拥有 `liaison.problem.review` 权限即可批准或驳回。审核权限通过发展端既有显式权限绑定到指定账号，不要求用户拥有主站管理员权限。系统记录实际审核人和时间。

### 7.4 开放揭榜

所有已登录同学可以查看开放问题，以个人或团队方式参与。同一问题允许多个个人或团队并行，不设置先到先得和唯一占有。参与记录包含团队名称、成员、简短方案、状态和加入时间。

首期不建设复杂邀请、团队等级或竞标排序。成员可以创建团队或申请加入已有团队；团队维护者确认加入申请并管理成员，联络中心处理明显异常记录。

### 7.5 问题社区

每个问题详情页包含四个区域：

1. 问题说明；
2. 揭榜团队；
3. 协作动态；
4. 成果墙。

协作动态只服务当前问题。已登录用户可以参与讨论，参与团队可以发布进展；作者可以修改自己的内容，联络中心可以隐藏违规内容。首期不建设跨问题信息流、关注关系或私信。

### 7.6 成果

每个团队可以提交一个或多个成果版本。成果包含标题、说明、链接或附件引用、提交时间和状态。联络中心可以把成果标记为“已提交”或“已采纳”；允许多个成果被采纳。成果被采纳后，问题仍可继续开放，直到联络中心主动结项。

### 7.7 后期升级接口

后期允许课题组或企业通过外部表单提交问题，生成待审核草稿；内部审核、公开问题、参与和成果模型保持不变。外部提交者不会因此自动获得发展端数据访问权限。

## 8. 必要数据与接口调整

数据库迁移只做增量变更，不修改已发布迁移文件。

- 经验库记录增加分类、标签、摘要和维护时间；
- 公告、咨询和提案增加负责人或处理期限等必要字段；
- 趣缘群体增加分类、负责人和公开联系方式；
- 活动增加报名截止时间、人数上限和联系人；
- 体育队伍增加赛季和训练安排；
- 联络模块新增问题、参与团队、团队成员、问题动态和成果记录。

列表接口统一支持有限的 `query`、状态、时间或组织筛选。筛选参数必须白名单验证；列表返回分页结构，避免数据增长后一次性读取全部记录。

详情接口返回页面所需聚合数据，但写操作仍按问题、团队、动态和成果分别提交，避免一个巨大更新接口。

## 9. 权限设计

- 普通同学只访问明确公开或属于自己的内容；
- 社工组织内容继续按组织成员等级和作用域判断；
- 创建、维护、审核、导出和管理成员使用不同权限动作；
- 联络揭榜审核权只赋给发展端负责人和团委书记对应的指定账号；
- 审核采用任意一人批准，不要求双签；
- 业务模块不得通过主站 `is_admin` 推导发展端领域权限；
- 后端无法读取有效授权时拒绝受保护操作；
- 权限变更、审核、批量导入、隐藏内容和成果采纳写入审计日志。

## 10. 错误与并发处理

页面分别显示：未登录、无权限、数据不存在、状态冲突、依赖不可用和一般网络失败。无权限与不存在在敏感资源上可以继续使用统一的不可枚举响应。

写操作期间只禁用相关记录或表单，不冻结整个页面。服务器成功后先显示确认状态，再刷新关联列表。刷新失败时保留已确认结果并提示用户稍后重试。

可能发生多人编辑的记录使用现有更新时间或后续版本字段检测冲突。冲突时不覆盖服务器内容，而是提示重新载入。

## 11. 测试策略

### 11.1 共用框架

- 页面标题、筛选、列表、抽屉和状态组件的可访问性测试；
- 桌面和移动宽度下的布局测试；
- 键盘操作、焦点返回和对话框测试；
- 深色主题如继续保留，验证与学习端主题变量兼容。

### 11.2 模块测试

- 每个列表页覆盖加载、空数据、错误、无权限和筛选；
- 每个详情页覆盖直接访问、记录不存在和返回导航；
- 每个编辑器覆盖字段验证、成功、失败和权限过期；
- API 覆盖字段白名单、作用域隔离和状态机；
- MySQL 集成测试覆盖新增迁移和外键；
- E2E 覆盖一个普通学生路径和一个维护者路径。

### 11.3 联络揭榜重点测试

- 两名审核人任意一人均可批准，其他人不能审核；
- 同一问题可存在多个并行团队；
- 团队只能管理自己的成员、动态和成果；
- 多个成果可以被采纳；
- 采纳成果不会自动关闭问题；
- 私密联系人不会通过公开 API 泄露；
- 所有审核、隐藏和采纳操作进入审计日志。

## 12. 实施顺序

多模块同步开发采用“共享底座先行、模块轨道并行”的方式：

1. 建立视觉变量、共用组件和路由骨架；
2. 为复杂模块建立空的列表/详情路由并保持旧功能可访问；
3. 并行迁移经验库、信息咨询、趣缘群体、活动、联络揭榜和体育模块；
4. 增加必要的增量数据库迁移与接口；
5. 将财务和平台治理接入统一外壳；
6. 完成响应式、权限、MySQL 和端到端回归。

任何阶段都不得用临时页面替换已经可工作的功能。模块迁移完成前，旧路径应继续可访问或提供明确重定向。

## 13. 验收标准

- 所有模块在视觉上与学习端属于同一产品；
- 普通用户首屏只看到阅读内容和一个清晰主操作；
- 页面不显示内部 ID、作用域类型或调试字段；
- 活动、信息咨询、联络揭榜和体育详情可通过独立 URL 访问和刷新；
- 经验库、趣缘群体和联络列表在移动端保持单栏可读；
- 既有功能和权限测试继续通过；
- 新增字段有迁移、类型、API 和 UI 测试；
- 联络揭榜完成代录、任一审核人批准、多团队参与、动态和多成果采纳闭环；
- 无发展端权限的用户不能通过手工 URL 或 API 绕过限制；
- 代码不再把新增业务继续集中到原有大型页面文件。
