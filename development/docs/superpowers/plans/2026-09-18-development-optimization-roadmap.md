# 发展端现有功能优化与上线计划

> 基线日期：2026-09-18。本文是跨模块路线图，不直接授权发布或修改主站。各阶段开始实施前，可按本文验收项拆成独立的代码任务。

## 目标与边界

把现有发展端 Demo 打磨为可以从 FREE-BBS 主站进入、在白名单内试用、可持续维护的产品。主站已经上线学习世界、课程入口、讨论区和个人工作台；公开访问 `/development` 仍显示施工页，并写明计划随 V1.1 于 2026 年 10 月上线。发展端应延续主站的蓝黑、青色、暖白色、字体与导航语言，同时建立自己的活动和组织业务体验。

本轮只完善现有模块：工作台、经验库、信息与咨询、资源、体育代表队、活动、趣缘群体、财务治理、权限与模块管理，以及活动内的「今日随机发现」和「我要上学生节」。不增设新的独立模块，不把尚未发布的 frEE bbs MAP 链接伪装成可用入口，不把演示账号或演示数据带入生产。

## 当前基线与待解决问题

| 方面       | 已有基础                                                                                          | 上线前缺口                                                                                         |
| ---------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 主站衔接   | Web 约定挂载 `/development/`；API 约定 `/api/development/v1/`；已有主站 `GET /api/auth/me` 适配器 | 真实主站 Token、登录/退出/过期、深层链接和异常场景尚需联调；主站公开入口仍为施工页                 |
| 准入和权限 | 服务端角色、动作、资源、作用域及 Tag；本地 Demo 身份切换                                          | 用户要求的「仅白名单可进入发展端」不能用现有 Demo 用户 allowlist 代替；必须在生产入口和 API 层落实 |
| 页面与视觉 | 已有统一外壳、模块路由、深浅主题、卡片、响应式布局                                                | 页面首屏仍偏模块清单与后台工作台；卡片密度、层级、按钮用语和主站的产品叙事尚未统一                 |
| 业务流程   | 活动、报名、经验阅读、咨询、资源揭榜、代表队、群体、财务和学生节投稿/审核已有页面与接口           | 需要以真实身份、真实数据验证普通同学和各中心人员的完整任务；补齐失败、空状态和内容维护责任         |
| 发布运维   | MySQL 迁移、构建检查、部署、健康探针、数据库备份与回滚文档已具备                                  | 尚需生产配置、真实 MySQL 与主站联调；学生节媒体文件需要与数据库配套备份和恢复演练                  |

## 推进顺序

### 阶段 0：冻结首批范围，建立验收基线（P0）

**交付**：一张「角色 × 入口 × 操作 × 数据可见性」矩阵，以及每个现有模块的负责人、首批真实内容和关键用户任务清单。更新 `docs/README.md` 的模块与路由说明，使其与 `apps/web/src/app/module-manifests.ts`、`apps/web/src/app/router.tsx` 和现有专题文档一致。

**验收**：矩阵至少覆盖普通同学、文艺/体育/联络/权发中心部员与部长、领域负责人、团委负责人和平台管理员；明确学生节未同意展示作品的查看范围，以及财务、咨询、代表队资料的访问边界。每项首批内容有长期维护人，不使用 `database/seeds/001_demo.sql` 充当生产内容。

### 阶段 1：主站身份与白名单闭环（P0，可与阶段 2 并行）

**交付**：由主站登录后进入发展端的同源链路。主站保留公开施工页；只有白名单中的真实主站 UID 可以进入 `/development/`。准入白名单与进入后的业务角色分开管理：白名单只决定能否试用，模块权限仍由发展端服务端判断。登录、退出、身份过期和权限变更都能正确反映。相关实现边界在主站入口/反向代理、`apps/api/src/core/auth/`、`apps/web/src/core/auth/` 和部署配置。

**验收**：白名单用户从主站导航和深层链接均能进入，刷新后不丢会话；非白名单用户点击入口或直接输入深层链接仍只看到施工页，调用受保护 API 也取不到发展端数据；退出主站后访问立即失效。生产构建不出现「预览身份」切换。用真实主站 `/api/auth/me` 返回值而非 Demo stub 验证，记录与主站负责人的联调结果。

### 阶段 2：按主站语言收敛视觉与导航（P0）

**交付**：把现有 `apps/web/src/styles/tokens.css`、`theme.css`、`shell.css`、`components.css` 作为单一视觉基线。统一侧栏宽度、标题层级、间距、卡片网格、状态标签和主次按钮；同一排卡片等高，内容过长时换行且操作区保持对齐。工作台首屏突出「最近内容/待处理/常用动作」而非重复侧栏；活动页保留学生节置顶入口和今日发现，但控制首屏信息量。经验库、资源、体育、趣缘群体使用一致的列表与详情阅读节奏。

**验收**：主站和发展端并排检查时，品牌色、字体、导航行为和按钮层级能够被识别为同一产品；桌面 1440px、平板 900px、手机 390px 均无横向溢出；所有列表卡片的边界、间距、标题与底部操作对齐；键盘可达、焦点可见，深浅主题对比度通过现有主题契约检查。保留发展端的业务特色，不复制学习世界的知识岛动效。

### 阶段 3：用现有功能形成完整使用路径（P0）

**交付**：优先打通四条任务链，而不是增加功能数量。

1. **普通同学**：主站进入 → 查看活动/今日发现 → 活动详情和报名/取消报名 → 查看个人状态；可继续进入经验详情、趣缘群体和公开资源。
2. **组织人员**：维护活动、经验、咨询或资源问题 → 提交/审核/发布 → 普通同学看到允许公开的结果；操作失败有明确反馈。
3. **学生节**：投稿并选择是否展示 → 审核人员查看/通过/拒绝/撤下/重新审核 → 同意且审核通过的作品进入展示流；私密作品始终不进入公开列表。
4. **领域人员**：体育代表队、财务治理与权限管理按既有作用域操作；跨中心账号不能越权查看或修改。

**验收**：每条链有负责人提供的非敏感真实样例数据和可重复的验收脚本；列表、详情、空状态、加载失败、权限不足与返回导航文案一致。以普通同学、各中心角色、团委负责人和管理员分别走查；关键写操作的服务端权限测试与审计记录通过。

### 阶段 4：白名单试运行与发布门槛（P0）

**交付**：按 `docs/production-release-checklist.md` 与 `docs/server-deployment.md` 完成 MySQL 迁移、生产配置、同源路由、健康检查、备份/恢复和回滚演练。学生节 `FESTIVAL_UPLOAD_DIR` 使用持久目录；数据库与视频文件作为一组恢复。先让覆盖普通同学、投稿审核人员、各中心负责人和管理员的白名单成员试用，再决定是否扩大范围。

**验收**：`npm run check`、MySQL 集成检查、production auth 端到端检查、桌面/手机关键路径通过；生产环境没有 Demo 模式或 Demo seed；服务端拒绝越权访问；上传中断、媒体丢失、数据库回滚和身份服务不可用均有可执行处置办法。记录每次试运行反馈、问题责任人、修复结果和发布判定。未满足任一门槛时继续保持主站施工页，不因目标月份而跳过门槛。

### 阶段 5：试运行后的小步完善（P1）

只根据试用数据和反馈继续改善现有模块：缩短活动发布及审核步骤，改善经验内容检索与维护，优化资源揭榜、代表队和财务的高频操作。今日发现目前的偏好保存在浏览器本地，若跨设备同步确有需求，再设计服务端偏好；frEE bbs MAP 取得真实 HTTPS 跳转链接后，按现有配置机制开放入口。两项都不阻塞首批白名单试运行。

## 实施分工与依赖

| 工作包                 | 主责                         | 依赖                          | 可独立验收的结果                           |
| ---------------------- | ---------------------------- | ----------------------------- | ------------------------------------------ |
| 主站入口、身份、白名单 | 主站维护者 + 发展端平台核心  | 双方确认 UID 与登录契约       | 公开施工页与白名单深链分别工作，API 无越权 |
| 视觉、导航、响应式     | 发展端前端 + 主站设计维护者  | 主站当前视觉基线              | 三种屏宽与双主题的页面走查通过             |
| 现有业务与内容         | 各中心模块负责人 + 平台核心  | 阶段 0 的角色矩阵和内容责任人 | 四条任务链与权限测试通过                   |
| 数据、媒体、发布       | 部署/数据库负责人 + 平台核心 | 前三项达到门槛                | MySQL、备份恢复、回滚和生产冒烟通过        |

优先级顺序为：阶段 0 → 阶段 1 与阶段 2 并行 → 阶段 3 → 阶段 4 → 阶段 5。阶段 3 的页面细节可随阶段 2 同步打磨，但最终验收必须使用阶段 1 的真实身份和阶段 4 的生产等价数据环境。

## 成功判定

首批成功不是「九个模块都出现」；而是白名单成员能从主站顺利进入、完成上述真实任务、只看到有权看到的数据，并愿意再次使用。公开用户仍看到主站施工页。所有不能稳定维护内容、不能通过权限与数据恢复验证的功能继续留在受控试运行范围内。
