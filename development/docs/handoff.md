# FreeBBS 发展端协作与交接指南

这份文档写给第一次接触 FreeBBS 发展端的协作者，也可以直接交给 Codex 作为任务背景。它不代替需求讨论、代码审查或生产授权，而是帮助接手者先对齐事实：这个项目为什么存在、代码已经做到哪里、哪些事情仍未完成，以及开始工作前应该检查什么。

> 状态快照：生产与 GitHub 状态沿用 2026-08-20 的最后一次只读核验；统一模块框架代码快照更新至 2026-09-14。GitHub、服务器和线上状态会变化，涉及这些内容时必须重新核验，不能只依赖本文。

## 先理解这个项目

FreeBBS 发展端是 FreeBBS 主站下的独立业务子页面，约定挂载在 `/development/`。它承载组织传承、信息咨询、个人成长档案、活动协作、联络资源、体育代表队和财务治理等功能，同时复用主站的登录身份和基础用户信息。

“复用主站登录”不等于“和主站写在同一个仓库里”。两个仓库的职责不同：

- [`Free-BBS/freebbs-web`](https://github.com/Free-BBS/freebbs-web) 是主站，负责登录状态、基础身份和首页入口；
- [`Free-BBS/Free-bbs-Development`](https://github.com/Free-BBS/Free-bbs-Development) 是发展端，负责自己的页面、API、业务数据、细粒度权限和审计；
- 生产环境计划通过同一个域名提供服务：Web 使用 `/development/`，API 使用 `/api/development/v1/`。

项目的核心原则是“共享身份，不共享无限权限”。发展端不建立第二套账号密码，也不会因为某人在主站拥有某个身份，就自动给他全部发展端管理权限。

## 怎样理解“已经完成”

交接时最容易出现的问题，是把几种不同状态混在一起。本文统一使用下面四个词：

- **已实现**：代码和测试已经存在；
- **已验证**：相应检查曾经通过，但仍应在当前提交上重新运行；
- **已合并**：代码已经进入远程默认分支；
- **已部署**：生产服务器已经运行该提交，并完成线上冒烟检查。

本项目的平台 MVP 已实现、已验证并通过 PR #1 合并，但截至本快照日期，不能据此声称发展端已经完成生产部署。

## 当前能力

仓库目前是一套完整的 TypeScript workspace，而不是页面原型。主要组成如下：

- `apps/web`：React Web，基础路径为 `/development/`；
- `apps/api`：Express API，版本化前缀为 `/api/development/v1`；
- `packages/contracts`：Web 和 API 共享的类型与接口契约；
- `database/migrations`：MySQL 迁移；
- `database/seeds`：只用于本地或测试环境的演示数据；
- `deploy`：Nginx、systemd、Docker 和环境文件模板；
- `scripts`：迁移、备份、管理员初始化和发布脚本；
- `tests`：浏览器 E2E、部署配置和运维流程测试；
- `.github/workflows`：CI、数据库迁移和生产发布工作流。

领域模块已经形成统一入口：

| 模块                     | 当前能力                                 | 建议长期维护方                 |
| ------------------------ | ---------------------------------------- | ------------------------------ |
| 经验库 `knowledge`       | General 与社工组织内容、受众和作用域控制 | 核心组定义结构，各组织维护内容 |
| 信息与咨询 `information` | 信息发布、咨询和提案池维护               | 权益发展中心                   |
| 个人成长档案 `growth`    | 活动报名足迹、领域统计与成就称号         | 平台核心组                     |
| 活动 `events`            | 时间地点、简介、详情、时间线与进度       | 核心组维护流程，各团队扩展活动 |
| 联络揭榜 `liaison`       | 真实问题代录审核、并行团队、动态与成果   | 联络中心                       |
| 体育代表队 `sports`      | 代表队、队长作用域、成员管理和 CSV 导入  | 体育中心及各代表队负责人       |
| 财务治理 `finance`       | 组织范围内的财务记录和审核               | 团委或财务治理负责人           |
| 权限与模块管理 `admin`   | 角色、Tag、作用域、模块状态和审计        | 项目负责人 / 平台核心组        |

工作台路由仍然存在，但导航中不再重复展示“工作台”入口。管理入口只对最高权限管理员展示，服务端仍会独立校验权限；没有权限的用户不能只靠修改前端地址绕过限制。

复杂模块使用可直接访问和刷新的详情路由：信息提案为 `/information/proposals/:proposalId`，活动为 `/events/:activityId`，联络问题为 `/liaison/problems/:problemId`，体育队伍为 `/sports/:teamId`。个人成长档案入口是 `/growth`；旧 `/interest-groups` 和 `/clubs` 地址只保留兼容跳转，旧群体数据及接口暂不破坏性删除。完整表格和数据约定见[统一模块框架技术说明](./technical_design.md)。

## 身份、权限与数据边界

生产模式下，发展端通过 Bearer Token 请求主站 `GET /api/auth/me`，再把主站身份映射为发展端主体，并加载发展端内部角色和 Tag。该接口的真实响应契约、超时和异常行为仍需要和主站生产环境完成联调。

发展端权限不是单一的“管理员/普通用户”开关，而是由角色、动作、资源、作用域和 Tag 共同决定。一个人可以属于多个组织，并在不同组织拥有不同等级。体育代表队队长是与基础角色并列的 Tag，而且必须绑定具体代表队作用域。前端隐藏按钮只是交互表现，API 的默认拒绝、作用域检查和审计才是最终边界。

本地开发默认使用 `memory + demo`，方便预览不同身份。进程停止后，内存数据会恢复到固定初始状态。生产必须使用 MySQL；演示 seed 不能作为生产初始化方案，也不能把演示 UID 当作真实账号。

## 五分钟开始本地工作

要求 Node.js `>=20.19.0`。在仓库根目录执行：

```powershell
npm ci
npm run dev
```

然后访问：

- Web：`http://localhost:5173/development/`
- 工作台：`http://localhost:5173/development/dashboard`
- API 健康检查：`http://127.0.0.1:3100/api/development/v1/health`

常用演示身份包括：

| UID                    | 适合检查的场景                 |
| ---------------------- | ------------------------------ |
| `demo-student`         | 普通同学可见内容和越权保护     |
| `demo-admin`           | 最高权限后台和模块管理         |
| `demo-rights-member`   | 权益发展中心与提案池           |
| `demo-liaison-member`  | 联络中心与趣缘群体维护         |
| `demo-sports-lead`     | 体育负责人、组织财务和代表队   |
| `demo-sports-director` | 体育部长与 CSV 名单导入        |
| `demo-captain`         | 仅在具体代表队内生效的队长 Tag |
| `demo-tuanwei-lead`    | 团委负责人和跨组织财务审核     |

如果 Windows 环境运行 `npm run dev` 时出现 `spawn EPERM`，先判断是否为执行环境限制，不要直接修改业务代码。可以分别启动 API 和 Web，或在允许创建子进程的终端中运行。更完整的环境变量和 MySQL 联调步骤见[本地开发与完整预览](./local-development.md)。

提交前至少运行：

```powershell
npm run check
npx playwright install chromium
npx playwright test
```

`npm run check` 包含 lint、格式、类型、单元与接口测试、运维和工作流测试，以及生产构建。Playwright 负责真实浏览器中的身份、导航、权限、提交和响应式行为。

需要 MySQL 的检查必须单独执行并如实记录：

```powershell
npm run test:mysql
npm run test:e2e:production
```

前者连续执行两次迁移后检查适配器一致性；后者使用构建产物、主站身份 stub 和 MySQL 验证生产形状。没有数据库服务时，这两项是“未验证”，不是“通过”。

## 统一模块框架的维护边界

- 迁移 `008_module_readability_fields.sql` 增加经验库、信息、趣缘群体、活动和体育所需的可读性字段；迁移 `009_liaison_problem_board.sql` 建立联络问题社区的五组表。已发布迁移不得回写，后续变化新增编号文件。
- 联络问题首期仍由联络中心代录。`platform.super_admin`（发展端负责人）和 `affiliation.tuanwei_lead`（团委书记/负责人）拥有独立的 `liaison.problem.review`，任意一人即可审核；`admin.manage` 或联络维护权限本身不能替代审核动作。生产账号通过治理台或管理员初始化流程授予角色，不把真实 UID 写进代码。
- 普通同学收到的联络问题投影不含 `internalContactNote` 和 `reviewNote`。只有记录所有者、维护者或审核者获得内部字段；前端不得用未经检查的类型断言把公开响应当作内部记录。
- 后期外部课题组或企业投稿应进入独立的候选提交资源，由联络中心核验和脱敏后复用现有代录与审核流程。外部提交不能直接生成公开问题，也不会自动获得发展端账号或读取权限。

## 协作者应该怎样分工

如果任务涉及主站身份对接、共享契约、权限模型、Tag、审计、模块注册、数据库基础设施或部署流程，应由平台核心组负责或先经过核心组评审。这些部分会影响所有领域模块，不适合由单一业务团队自行改变。

领域团队可以独立开发自己的页面、接口和数据逻辑。例如体育中心可以继续开发代表队系统，权益发展中心可以完善提案池，联络中心可以维护揭榜问题；但它们必须复用统一身份、权限、审计和 `packages/contracts`，不能另建账号系统，也不能直接读取或修改其他模块的数据。

认领任务时，至少写清楚：目标用户、长期负责人、数据归属、需要的权限动作与作用域、接口变化、验收方式和后续维护安排。需求还不清楚时，先形成 Issue 或设计说明，不要从页面按钮直接反推权限和数据结构。

## 新协作者的推荐接手顺序

1. 阅读本文和[总体技术设计](./overall-technical-design.md)，先确认任务属于平台核心还是领域模块；
2. 检查远程 `main`、开放 PR、当前分支和工作树，不依据本地旧分支判断项目进度；
3. 运行本地预览，分别用普通同学、领域成员和最高权限管理员身份检查现状；
4. 阅读目标模块的 Web、API、共享契约和测试，明确现有接口再设计改动；
5. 在 Issue 或 PR 中写清责任人、权限、数据边界和验收标准；
6. 小步实现并补充测试，提交前运行与风险相称的验证；
7. 只有在获得明确授权后，才进行 GitHub 设置、合并、生产凭据或服务器变更。

## 给 Codex 的接手说明

可以在新的 Codex 任务中直接说：“请先完整阅读 `README.md` 和 `docs/handoff.md`，核验其中的动态状态，再继续我的任务。”本文提供背景，但不会扩大用户对 Codex 的授权范围。

### 开始工作前必须检查

- 用 `git status --short --branch` 确认当前分支和未提交改动；
- 用 `git worktree list` 确认是否处于隔离工作树；
- 检查 `git log`、远程 `main` 和相关 PR 的当前状态；
- 阅读与任务直接相关的 README、设计、契约、测试和工作流；
- 区分本地演示、CI 验证和生产状态；
- 保留用户已有改动，不把换行或索引状态造成的假差异当成业务修改。

### 可以在任务范围内直接执行

- 阅读代码、配置、提交历史和测试；
- 运行本地静态检查、测试、构建和预览；
- 在用户要求修改功能时，在隔离分支中实现并验证；
- 对明确范围内的文档、代码和测试进行一致性更新；
- 报告可复现的错误、风险和未验证假设。

### 必须先取得明确批准

- 合并或关闭 PR、强制推送、删除分支或工作树；
- 修改 GitHub ruleset、environment、Secrets 或组织设置；
- 连接生产数据库并执行迁移、seed、恢复或直接 SQL 修改；
- 改动生产 Nginx、systemd、Docker、TLS、DNS 或服务器文件；
- 读取、创建、替换或传播真实凭据；
- 任何会影响主站、其他协作者或真实用户的外部写操作。

### 不得假设

- 不得把“代码存在”写成“已经上线”；
- 不得假设 PR #2、服务器引导或部署已经在本文之后完成；
- 不得假设普通 SSH 账号拥有 sudo 或 Docker 权限；
- 不得用 demo 身份、内存数据或 seed 代替生产身份和数据；
- 不得只凭前端隐藏判断权限正确；
- 不得为了让检查通过而删除部署安全测试或放宽权限边界。

### 完成任务时应汇报

- 修改了哪些文件和行为；
- 运行了哪些检查，结果是什么；
- 哪些事项没有验证，以及原因；
- 是否创建了分支、提交或 PR；
- 是否触碰外部系统、GitHub 设置或服务器；
- 下一位协作者继续工作所需的最短步骤。
